# Disposable validation gate

## Current evidence

The C# solution, TLS fixture suite and pinned Python imap-tools client test run locally. The Docker image builds from digest-pinned official .NET SDK and ASP.NET Core runtime bases. HTTP health tests cover readiness, dependency failure, hostname verification, credential-free probing and graceful shutdown. No official Bridge instance, live Proton account, Paperless worker, OCR pipeline or Kubernetes deployment has been tested. The user confirmed that no disposable Proton account is currently available. This gate remains pending; do not describe synthetic tests as a live Bridge proof.

## Official Bridge prototype

1. Provision a disposable Proton account and an isolated Paperless instance. Install an official, unmodified Bridge release and record its exact version. Sign in and complete 2FA in Bridge, create `Paperless-imported` through Proton, and export only its public TLS certificate to proxy trust. Provide the test host, generated Bridge credentials through the Paperless secret mechanism, and explicit permission for the fixture messages/label. Never submit credentials in an issue, test log or repository.
2. Deliver disposable PDFs covering inline and attachment dispositions, read/unread states, starred/unstarred states, mixed-case/absent filenames and multiple PDFs in one email. Include two independent byte-identical deliveries and distinct messages sharing Message-ID. Record source Inbox UIDVALIDITY/UIDs, read/star flags and membership using a separate read-only client. Verify wrong credentials, wrong CA, wrong hostname, expired certificate and replaced certificate fail. Test Bridge STARTTLS and implicit TLS separately; neither may downgrade to plaintext.
3. Fetch complete `BODY.PEEK[]` octets repeatedly before and after COPY, across label and Inbox folders and after Bridge/proxy restart. Compute hashes privately without printing message contents. Verify exact octet stability, COPYUID support and that `UID COPY ... Labels/Paperless-imported` adds membership while retaining Inbox UID, read state and stars. Check Proton's UI as well as Bridge's mailboxes. If the stock Bridge returns no usable COPYUID or changes octets across folders, stop: the current identity design is not validated and must change before release.
4. Run the real Paperless 3.3.4 rule with inline attachments enabled, blank filename filters, age limit zero and the tag action. Await all consumer tasks and the separate post-consume label action, then poll again and restart both applications. Assert each PDF is represented once, both identical deliveries have independently handled source UIDs, all source emails remain in Inbox, read/star states are unchanged and labels are present. Paperless may intentionally deduplicate identical document content; distinguish document-level deduplication from missed email processing. Test two proxy client sessions and one active Paperless polling schedule. Failed document consumption must not add the label.
5. Interrupt the proxy before COPY, after remote success and before journal completion; retain state and retry. Confirm safe unique recovery and explicit failure on ambiguous identical deliveries. Simulate Inbox and label UIDVALIDITY changes without touching real mail: Inbox reset must block even new sessions until queued actions are drained and explicit recovery is performed. Test external label changes, missing labels, state loss/corruption, certificate rotation, concurrent COPY requests and network disconnects. Keep all evidence scrubbed. Do not delete fixture messages or remove labels without separate authorization; proxy clients cannot perform cleanup.

Estimated hands-on gate time: 45–60 minutes after a disposable account, Bridge and Paperless are ready; OCR/task completion and account setup can take longer. No test host or mailbox action is authorized by this document alone.

## Review and release

1. Review source, protocol limitations, identity ambiguity and the live gate evidence. Keep `--experimental` until official Bridge byte stability, COPYUID semantics and full Paperless ingestion have passed. The test fixture does not implement Proton's backend behavior. Record tested OS, architecture, Bridge, Paperless and MailKit versions in release notes; verify upstream label PR status again.
2. Use .NET SDK from `global.json`, restore with `dotnet restore --locked-mode`, and run `PAPERLESS_TEST_PYTHON=/path/to/python dotnet test -c Release --no-restore` after installing the hashed test dependency. Build with `docker build -t proton-bridge-bridge:review .`. Inspect NuGet vulnerability reports and dependency licenses; no upstream source code is vendored. CI runs on pull requests and pushes and produces only a review artifact/local image.
3. Publish a framework-dependent native build with `dotnet publish src/ProtonBridgeBridge -c Release --no-restore -o artifacts/ProtonBridgeBridge /p:UseAppHost=false`. Archive it with its license, release notes and SHA-256 manifest. Review container base digests, run the same disposable gate on the image and record its resulting digest. Do not include certificate/private-key/state/config files in artifacts.
4. After review, create the intended version tag and publish native archives/container image manually to the chosen release destination. No destination is configured and CI has no publish permission. Record artifact checksums, image digest, source commit and gate evidence. Keep Bridge installation and updates independent.
5. For upgrades, stop polling and let active post-consume actions finish, stop the proxy, back up its state, then replace the binary/image. Keep state/schema compatibility explicit; current files are prototype JSON records plus a mailbox epoch file. Roll back with the matching state backup only after reviewing remote label changes. Never restore old state blindly while pending actions remain. Re-run the disposable gate after Bridge changes that might alter message octets or folder UIDs.
